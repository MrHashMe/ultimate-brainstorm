# Troubleshooting

Start with `doctor`. Inside your agent, type the command followed by `doctor` (for example `/ultimate-brainstorm
doctor`). In a terminal:

```
py -3 <kit>/install/install.py doctor           (macOS/Linux: python3 ...)
py -3 <kit>/install/install.py doctor --live    (also tests each model family with one tiny call)
```

Every check prints PASS, WARN or FAIL with a fix. Nothing is changed by `doctor`.

A stopped run is never lost. After fixing the cause, type `continue` (for example `/ultimate-brainstorm continue`)
in any agent, or run `~/.ultimate-brainstorm/bin/ub run --continue` in a terminal.

## When the pipeline stops (BLOCKED)

When the pipeline cannot go on, it shows a short explanation and one or more fix commands. The common ones:

| What you see | Why | Fix |
|---|---|---|
| a family "not logged in", "auth" or "invalid api key" | a CLI login expired or a key is wrong | `codex login`, `kimi login`, or run `claude` once and sign in; check the key variable (see [FAMILIES.md](FAMILIES.md#setting-a-key)); then `continue`. The family stays unused until you log in again and run `continue` (same host or another) or `run --continue`, or retry the BLOCKED step: each detects it again. The run can also go on without that family (marked PROVISIONAL) |
| "network" or "sandbox" errors from inside Codex | Codex's sandbox blocks the network for commands it starts | approve the `ub` command with "always" for this session when Codex asks, then `continue`. Or run the pipeline in a terminal: `ub run --continue` |
| "Your agent stops background work before model calls finish" | the host kills background processes (some IDE terminals and sandboxes do) | run it in a terminal: `<runner> run --continue "<run>"` (the card shows the exact line), or raise the agent's command timeout (see [HOSTS.md](HOSTS.md)) |
| a job failed with "killed: the worker was stopped by a signal" | the worker got SIGTERM, SIGBREAK or Ctrl+C before it finished (a host or the system stopped it; `ub stop`, a redo and the kit's own relaunch of a dead job never cause this) | its fallback runs; if the step is BLOCKED, run the rest in a terminal (`<runner> run --continue "<run>"`, the card shows the exact line) or retry the step with `next` |
| "kimi 1.x" / "upgrade: npm install -g @moonshot-ai/kimi-code, then kimi migrate" | the old archived `kimi-cli` is installed | run exactly that; the old `~/.kimi` folder is then migrated |
| "run: kimi login" | Kimi Code is installed but not logged in | `kimi login`. Note: setting `KIMI_API_KEY` does not log the Kimi Code CLI in |
| Kimi fails on Windows / "bash not found" | Kimi Code needs Git Bash on Windows | install Git for Windows (`winget install Git.Git`), or set `KIMI_SHELL_PATH` to a bash.exe; restart Kimi |
| "budget" question (GB) or a BLOCKED budget card in full-auto | the next job could pass the run's request cap (quick 60, standard 180, deep 600, proposal 90 backend requests) | answer GB with a higher number, or stop. In full-auto run the card's command, `ub budget "<run>" --max-calls N`: the run goes on by itself. Never edit run.json by hand |
| "seed leak" | a prompt for an idea generator would have contained your own seed ideas (this protects the "human ideas first" rule) | usually caused by editing run files by hand; undo the edit or `redo` the step the card names |
| "origin label" | a judge prompt would have revealed where an idea came from: it holds one of this run's alias IDs (`S2-04`, `H-03`, ...) or an origin label (`Origin: gpt`, `**Origin:** gpt`, `(origin: human)`, `strategy: S2`); ordinary words such as `generated by a solver`, `written by human volunteers`, `Deployment strategy: blue-green` or `Storage strategy: S3 buckets` never cause it | remove the text from the file the card names, then run the `redo` command the card gives (it prepares the judge prompts again; for the architecture judges, `next`) |
| "not enough results" for a step (for example fewer than 3 of 5 idea strategies) | several families failed for the same step | fix the family (see the first rows), then `continue`; or `redo <step>` |
| a job "refused by policy" | the job would break your privacy answers or a vendor rule (for example the GLM Coding Plan over HTTP) | nothing is wrong with your setup; the card says which rule. Change the privacy answer only if you mean it |
| "another session is driving this run" | another agent or terminal is driving the same run right now (a terminal waiting for your answer does not count, except a `ub run` of kit 2.0.x: it keeps the run while it waits) | let it finish, or stop that session; the card's `then` retries your command. A kit 2.0.x terminal waiting for an answer: answer it there, or close it (Ctrl+C). A crashed session never blocks: the operating system frees its lock |
| "another session took over this run; this one stopped without saving" (BLOCKED) | this session was suspended or stalled for more than 2 minutes while a kit 2.0.x session drove the same run, and that session took the run over; or a kit 2.0.x session started in the instant this one rewrote its record in `.ub/lock.json`, and took the run | run the card's fix (`next`); it waits until the other session is done. Nothing of the other session's work is lost, except rarely when this card came from `answer` or `done`: that change may have been saved anyway, over the other session's last change. Once the other session is done, check `ub status`, and answer again (or run `done` again) if the gate or task is still pending |
| "A redo could not move <file> to _superseded/ yet" | another program (an editor, a viewer, a sync client, an antivirus scan) has that file open | close it, then run the card's fix; the redo finishes its moves before anything else runs |
| a DONE card "stopped (user)" | `stop` paused the run | `continue` resumes it (the agent's own `next` keeps the stop); nothing that finished is lost |
| the stop card says "N worker(s) could not be verified (pid ...)" | the kit cannot tell whether they are its workers (`ps` is unavailable or failed, or the worker recorded no identity), so it did not kill them | check the pids (`ps -p <pid>` / Task Manager); stop the ones that are `family.py job` workers of this run by hand, then `continue` |
| a job `refused` with "codex used <type> on a tools=... job" for an item type the kit does not know | a newer Codex emits a new kind of event | if it is harmless, add it to `backends.codex-cli.allow_items` in `~/.ultimate-brainstorm/families.json`; tool types can never be allowed |
| "host task <id> is in progress in another session" | another agent session was handed that host task (or batch of sub-agent jobs) and is still working on it | finish it there, or take it over here with `continue` (in a terminal: `ub run --continue`) |
| "host task <id> was taken over and accepted from another session" | you took the task over in another session, and this one changed its files afterwards | check the named files (the other session's version was accepted); to run the task again, use the `redo` command the card shows |
| "scripts/pipeline.json is inconsistent" or a missing or broken template (for example `index.html.tpl` or a handoff seed) | a kit file was edited or an update was cut short | `install.py update` (or `install.py install` from your clone), then `continue` |
| "kit version differs" | the run was started with another kit version | usually fine; if something breaks, finish the run with the version that started it, or `redo` from a stage |
| "path is N characters, more than the 259 Windows allows without long-path support" | the run folder is deep and Windows long paths are off | start the run in a shorter folder (`ub init --root C:\ub ...`) or enable long paths (Group Policy "Enable Win32 long paths", or the registry value `HKLM\SYSTEM\CurrentControlSet\Control\FileSystem\LongPathsEnabled` = 1; the python.org installer offers "Disable path length limit"), then `continue`. `ub doctor` shows the setting |
| "the run folder <path> holds '$', which bash and PowerShell change inside the double quotes of the card commands" (or a backtick or a double quote) | the project folder's name has a character that every card command would lose on its way through the shell | start the run in another folder (`ub init --root C:\ub ...`). A run that already sits in such a folder: move the folder, or resume it in a terminal with the `run --continue '<run>'` fix the card shows |
| "... starts with the command word stop, and the rest is not a run folder" (or continue, status, doctor) | your topic begins with one of the command words, which the skill would otherwise run as a command | start again with a mode word first, for example `/ultimate-brainstorm standard stop smoking coach for nurses`; to stop, continue or check a run, give its folder name (`ub list`) |
| step 12.12 stops with "10_ARCHITECTURE/decisions.json is not valid JSON" | the file was edited by hand into invalid JSON | the ADRs are left as they were; fix the JSON (the raw model output is in `10_ARCHITECTURE/_raw/`), then `continue`. New runs cannot get there: an invalid `decisions.json` fails its contract and earns a repair call |
| the sign-off card lists lint FAILs or unresolved review findings | a generated architecture or proposal document still breaks a format rule after the automatic fix pass | they are also listed as open questions in the proposal. Reply `changes: <what to fix>` at sign-off (for proposal lint items: `changes: fix the lint items`), or `redo 12.14` to run the architecture fix pass again |
| the sign-off card lists `Lint P11 WARN, ONE-PAGER.md: ...` | a fix changed a figure or date in the proposal, but the one-pager still states the old one | reply `changes: fix the lint items` at sign-off; the fix step rewrites ONE-PAGER.md to match the sections |

`status` (for example `/ultimate-brainstorm status`) shows where a run is. `PROGRESS.md` in the run folder always shows
the current stage, the next step and which families are OK.

## Installer and doctor messages

| Check | Meaning | Fix |
|---|---|---|
| "no supported agent detected" (exit 3) | none of Claude Code, Codex, Kimi Code or ZCode was found | install one: `install.py install --with-clis codex --login` (or `claude`, `kimi`), or name the agent you will install later with `--agents kimi` |
| "exists (v1, not owned)" | a v1 copy of the skill is in the way | `install.py install --migrate-v1` (it is backed up first) |
| "skip-not-owned" | a folder named `ultimate-brainstorm` was not created by the installer | check what it is; `--force` backs it up and replaces it |
| "backup+update" | you edited an installed file | nothing to do; your version is saved in `~/.ultimate-brainstorm/backups/` |
| "duplicate skill" (FAIL) | the same skill is in two folders one agent reads, for example both `~/.agents/skills` and `~/.codex/skills` | delete the older copy (usually `~/.codex/skills/<name>`); Codex would otherwise list it twice |
| "claude family reclassified as glm" (WARN) | your normal Claude Code is set up to talk to Z.ai (or Moonshot) | fine if intended: the kit counts it as that family. For real Claude models, set up GLM with `claude-glm` instead and restore `~/.claude/settings.json` |
| version below minimum (WARN) | an agent is older than the native plugin route needs (Claude Code 2.1.268, Codex 0.156) | update it (`npm install -g @anthropic-ai/claude-code` or `@openai/codex`); until then the copy route is used |
| Node older than 22.20 (WARN) | CLI installs with npm (`--with-clis`) became manual | update Node, or run the printed manual commands |
| `... does not match its pinned SHA-256 ... not installing mattpocock-grilling` | the downloaded archive is not the pinned content | do not install it; check the network or proxy, then report it |
| `the marketplace <name> (...) was already registered and tracks commit ...` | an earlier registration of that marketplace tracks another ref | run the printed `plugin marketplace remove <name>`, then install again |
| `another install.py changed this install ... after this plan was made` / `runs became active after this plan was made` (exit 4) | the state changed while the plan waited | run the command again (after the run finished, or with --force) |
| `blocked rows present after the CLI install; only the CLI rows were applied` (exit 4) | with `--with-clis --yes`, the newly installed CLI's agent has a blocked row (for example a non-UTF-8 `AGENTS.md`) | fix the warning, then run the command again (the CLI stays installed) |
| Compound Engineering row is "manual" | the kit could not read Claude Code's marketplace list | in a Claude Code session: `/plugin marketplace add EveryInc/compound-engineering-plugin@compound-engineering-v3.28.2` then `/plugin install compound-engineering` |
| "families" WARN | a model family is not available (not installed, not logged in, or no key) | follow the note next to it; `doctor --live` confirms the fix |
| stale backups (WARN) | backups older than 90 days | delete old folders in `~/.ultimate-brainstorm/backups/` if you do not need them |
| "re-run with --yes" | the installer had no terminal to ask you | run it again in a terminal, or add `--yes` |
| "runs are active: <run> ... pass --force" | an install or update would swap the kit under running workers or a live driver | wait for the run, `ub stop <run>`, or pass `--force`; for "a kit 2.0.x session (pid P, ...)" answer it or close it (Ctrl+C in its terminal; `ub stop` does not end it), then run the command again |
| "another install.py is applying changes (.../install.lock is locked)" | another installer is running | wait for it to finish |
| "the marketplace ultimate-brainstorm is registered from <source>, not from the staged kit" | you installed the plugin another way (for example from GitHub) | remove it with the printed commands, or re-run with `--force` to replace it |
| "provenance check failed for <archive>" | gh attestation verify did not confirm that the repository's release workflow built the archive for its tag (no valid attestation, or gh could not reach GitHub) | do not install it; report it. If gh failed for another reason, such as the network, run the command again; if GitHub or Sigstore stays out of reach, run the printed check where gh reaches them and install that archive's extracted folder with `install.py update --source DIR` |
| "the release archive <name> holds kit <X>, not <Y> (its tag v<Y>)" / "the latest release is v<X>, older than 2.1.0" | the release's assets are not what its tag says, or an old release was marked latest | do not install it; report it (to install an older release on purpose, name it with `--tag`) |
| "provenance not checked" (note) | the GitHub CLI is missing or not signed in to github.com, or cannot reach Sigstore's trust root ("could not build its Sigstore verifier", for example behind a proxy), or the archive is local | fine to go on; `gh auth login` enables the check (`gh auth status --active --hostname github.com` shows the account the shims and `install.py update` use), and `--require-attestation` makes it mandatory |
| doctor `leftover:<path>` FAIL or WARN | an interrupted install left a staging folder | `install.py install` removes it |
| doctor `stack.<skill>.drift` WARN | a component skill changed after it was installed from its pinned commit | reinstall the component, or ignore it if you changed it on purpose |
| doctor `stack.<skill>.unpinned` WARN | a grilling or domain-modeling folder the installer has no record of (kit 2.0.x installed it unpinned, or it was copied by hand) is not the pinned content | unless it is your own skill, delete the folder and run `install.py install` |
| doctor `... could not be checked` / `could not be compared` WARN | doctor could not read a file in that skill folder (another program holds it open, no read permission, or it was removed meanwhile) | make the file readable (close the program holding it), then run `install.py doctor` again |
| "install-manifest.json has no record ... applying records it again" | an earlier install was interrupted | apply the plan; it records the copies and plugins again so uninstall can remove them |

## Windows notes

- **Python.** Use `py -3`. A plain `python` or `python3` may open the Microsoft Store instead (a stub in
  `...\WindowsApps\`). Install Python with `winget install Python.Python.3.12` if `py -3 --version` fails.
- **PowerShell will not run the `.ps1` launchers** ("running scripts is disabled on this system"): use the `.cmd`
  launcher instead (`%USERPROFILE%\.ultimate-brainstorm\bin\claude-glm.cmd`, which also works from PowerShell), or run
  the script with `powershell -ExecutionPolicy Bypass -File "$HOME\.ultimate-brainstorm\bin\claude-glm.ps1"`.
  Changing your execution policy is your decision; the kit never changes it.
- **Special characters.** The `claude`, `codex` and `kimi` commands installed by npm are `.cmd` files on Windows. The
  kit refuses arguments containing `" & | < > ^ % !` for them, because cmd.exe would misread them. Type such text
  inside the agent session instead of on the launcher's command line. Prompts never go on the command line, but the
  kit passes its own paths to these shims: keep UB_HOME, the project folder and the repository free of these
  characters when you use an npm `.cmd` CLI. `family.py detect` marks such a family unavailable with the fix, and a
  call that meets such a path fails at once with error class `config` and a reason naming the folder.
- **Git Bash.** Kimi Code needs it; Claude Code can use it or its PowerShell tool; Codex uses PowerShell.
- **Encoding.** All kit files are UTF-8. If a terminal shows garbled characters, run `chcp 65001` in cmd, or in
  PowerShell 5.1: `$OutputEncoding = [Console]::OutputEncoding = [System.Text.UTF8Encoding]::new()`. The `.cmd` and
  `.ps1` launchers (`ub`, `claude-glm`, ...) work when UB_HOME or Python sits under a profile folder with an accent
  (`C:\Users\José`); if launchers written by kit 2.0.x fail with "can't open file" there, run `install.py install`
  again to rewrite them.
- **Long paths or antivirus.** If a copy or rename fails during install, run the installer again: it works in a
  temporary folder and swaps it in at the end, so a failed attempt leaves the old install intact.

## Codex notes

- `$ultimate-brainstorm` not found: open `/skills` and use the name listed there (plugin skills can appear with a
  namespace), or check `install.py list`. Restart Codex after installing.
- Codex asks for approval on every model call: choose "always" for the `ub` command prefix.

## Still stuck

Run `install.py doctor --json` and `ub doctor --json` (inside a run: `status`), and keep the run folder's
`logs/calls.jsonl`: it lists every model call with its result and error class, with keys removed.
